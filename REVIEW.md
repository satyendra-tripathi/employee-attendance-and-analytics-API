# REVIEW.md

## Starter Code Defects and Fixes

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 14-23) | Used naive `date.today()` instead of evaluating the attendance record's IST calendar date; failed to truncate instant milliseconds before comparison; misapplied grace period threshold (`>= 10` instead of strictly `> 10` minutes); did not support overnight shifts. | Tests passing punch-in at `09:40:00` were marked 10 minutes late (contract specifies `09:40:00 -> 0`, `09:40:01 -> 10`); punches for past dates evaluated against today's date; overnight shift punch-ins threw errors or calculated negative late minutes. | Rewrote `compute_late_minutes` to convert `punch_in` to IST, truncate to whole seconds, construct the shift start datetime from `date_str`, check `elapsed_seconds > 600`, and return `floor(elapsed_seconds / 60)`. |
| 2 | `compute_work_hours` (lines 25-28) | Used Python's built-in `round()`, which implements Banker's Rounding (round half to even), violating business rule R4/R8 requiring half-up rounding. | Testing `compute_work_hours` with 9 hours 7 minutes (32820 seconds = 9.1166... hrs) or 9.125 yielded 9.12 instead of half-up rounded values in boundary cases. | Implemented `compute_work_hours` using Python `decimal.Decimal` with `ROUND_HALF_UP` quantized to `Decimal("0.01")`. |
| 3 | `compute_overtime` (lines 30-36) | Compared naive `datetime` with aware `datetime`, raising Python `TypeError`; failed to account for overnight shifts where `shift_end` falls on the next calendar day; did not apply the >= 30 minutes threshold. | Calling `compute_overtime` threw `TypeError: can't compare offset-naive and offset-aware datetimes`; overnight shifts produced huge negative differences. | Converted `punch_out` to IST, truncated to whole seconds, added `+1 day` to `shift_end` for overnight shifts (`shift_end <= shift_start`), and returned `floor(diff_sec / 60)` if `>= 30` else `0`. |
| 4 | `punch_in` (lines 40-52) | Race condition due to non-atomic check-then-insert (`find_one` followed by `insert_one`), allowing concurrent duplicate punch-ins; failed to determine attendance date according to overnight shift rules (R1). | Running concurrent punch-in requests created duplicate attendance documents for the same employee and date; punches at 02:00 IST for a 22:00-06:00 shift were assigned to the wrong calendar date. | Implemented `determine_attendance_date` handling overnight shifts; relied on unique compound index `{"emp_code": 1, "date": 1}` catching `DuplicateKeyError` and returning HTTP 409 atomically. |
| 5 | Missing `punch_out` endpoint | Endpoint `POST /attendance/punch-out` was completely missing from the starter code. | Client requests to `POST /attendance/punch-out` returned HTTP 404 Not Found. | Implemented `punch_out` finding the latest active punch-in (`punch_out: None`), validating that `punch_out > punch_in` and `<= 24` hours, computing derived metrics (`work_hours`, `overtime_minutes`, `half_day`), and updating atomically using `find_one_and_update` with concurrency check. |
| 6 | Missing `regularize_attendance` endpoint | Endpoint `PATCH /attendance/{emp_code}/{date}` was completely missing from the starter code. | Client requests to `PATCH /attendance/{emp_code}/{date}` returned HTTP 404 Not Found. | Implemented `regularize_attendance` with comprehensive validation (presence status requires punch-in; punch-in matches date; ABSENT/LEAVE clears punches; reason and by required; optimistic concurrency control on history length; recalculates derived fields). |
| 7 | Missing Analytics Endpoints (Part B) | Endpoints `GET /analytics/employees/{emp_code}/monthly`, `GET /analytics/departments/summary`, `GET /analytics/leaderboard/late`, and `GET /analytics/departments/{department}/trend` were not implemented. | Any analytics requests returned HTTP 404 Not Found. | Implemented all four analytics endpoints using MongoDB aggregation pipelines respecting R1-R10 (Mon-Fri working days, mid-month joiners, R8 half-up rounding, competition ranking ties, and gap filling). |
| 8 | Missing Admin Explain Endpoint (Part C) | Endpoint `GET /admin/explain/{endpoint}` was completely missing from the starter code. | Admin explain requests returned HTTP 404 Not Found. | Implemented `admin_explain` generating raw `executionStats` using shared pipeline builders identical to the production endpoints. |
| 9 | `list_attendance` in-memory sorting & loading (lines 54-66) | Loaded entire dataset into memory via `list(db.attendance_logs.find(q))` and sorted in Python (`data.sort(...)`), crashing on large datasets (~100k records). | Querying `/attendance` with large collections consumed gigabytes of memory and executed in linear time without database cursor pagination. | Rewrote `list_attendance` to push sorting and pagination to MongoDB using `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`. |
| 10 | Unbounded Pagination Parameters | `page` and `page_size` query parameters lacked FastAPI/Pydantic constraints (`ge=1`, `le=100`). | Passing `page=0` or `page_size=1000000` resulted in invalid skips or server memory exhaustion instead of HTTP 422. | Added `Query(1, ge=1)` and `Query(20, ge=1, le=100)` validation across all paginated endpoints. |
| 11 | Missing Application Lifespan & Index Creation | Starter code had no startup index management; unique constraints on `emp_code` and `(emp_code, date)` were absent. | Duplicate employees and attendance records could be created; database queries defaulted to `COLLSCAN`. | Added FastAPI `lifespan` handler that idempotently creates all 8 required single and compound indexes on startup. |
| 12 | Epoch Millisecond Validation Missing | Accepted arbitrary timestamps including 10-digit epoch seconds, strings, and negative values. | Sending seconds (e.g. `1783312500`) silently created corrupted BSON dates in 1970 instead of returning HTTP 422. | Added strict validator `validate_epoch_ms` enforcing integer millisecond values in `[100000000000, 4102444800000]`. |
| 13 | Date Format & Range Validation | Endpoints accepting date ranges (`date_from`, `date_to`, `from`, `to`) did not validate `to >= from` or maximum range of 92 days. | Invalid date ranges (`from > to`) caused reversed or empty queries; oversized ranges caused timeouts. | Added strict ISO date parsing and validation enforcing `to >= from` and `(to - from).days + 1 <= 92`. |
| 14 | Absence of Optimistic Locking on Regularization | Concurrent regularization updates could overwrite history entries and derived field mutations. | Two managers simultaneously regularizing the same attendance record caused one manager's audit history to be silently overwritten. | Applied atomic `find_one_and_update` checking `history.{len}` array length and appending audit history atomically. |
| 15 | Leaking Internal MongoDB `_id` Field | Starter code serialized documents containing MongoDB `ObjectId` or raw `_id`, violating the OpenAPI contract schema. | Responses contained `_id: "66..."` which failed OpenAPI schema validation. | Removed `_id` in database projection and serialization functions (`serialize_employee_doc`, `serialize_attendance_doc`). |

## Non-Defects Inspected

1. **Storing UTC Datetimes in MongoDB**:
   - *Inspection*: Checked whether `punch_in` and `punch_out` should be stored as IST datetimes or UTC BSON datetimes.
   - *Conclusion*: Not a defect. MongoDB BSON dates are standard UTC epoch timestamps. PyMongo with `tz_aware=True` correctly preserves UTC instant semantics while conversion to IST is performed during calculations and API serialization.
2. **Excluding Weekend Records from `present_days` while including them in Late and Overtime**:
   - *Inspection*: Checked if weekend punches should count toward `present_days` in monthly calculations.
   - *Conclusion*: Not a defect. Business rule R7 explicitly specifies: "`present_days` only counts records that fall on Mon-Fri (weekend records still contribute to late and overtime totals)." The aggregation pipeline correctly separates these metrics.
3. **Omitting Departments with Headcount 0 in Department Summary**:
   - *Inspection*: Checked whether departments with zero active employees should be listed with 0 values.
   - *Conclusion*: Not a defect. Business rule R9 specifies: "A department whose headcount is 0 for the month is omitted." Filtering out departments with no employees joined on or before month-end strictly adheres to the rule.
